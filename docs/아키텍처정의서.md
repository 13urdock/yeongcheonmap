# 영천 홍보지도 앱 — 아키텍처 & 파일 구조 정의서

> 목적: AI가 구현하되, 사람이 나중에 구조적으로 검토 가능하도록 **폴더 구조·레이어·파일 분리 규칙**을 못 박는다.
> 스택: 프론트 Flutter + Provider / 백엔드 NestJS(Node.js) / DB PostgreSQL / 이미지 외부 스토리지.
> 레포 분리: 프론트·백엔드 저장소를 **각각** 둔다(레포 2개).

## 0. 핵심 원칙 (모든 코드에 적용)

1. **1파일 1역할.** 한 파일은 한 가지 책임만 가진다. 역할이 둘 이상이면 파일을 나눈다.
2. **역할이 명확해질 때까지 쪼갠다.** "이 파일이 무슨 일을 하는가"를 한 문장으로 말할 수 없으면 아직 덜 쪼갠 것.
3. **파일 길이 상한(가이드)**: 한 파일 약 200줄을 넘기면 분리를 검토한다(하드룰 아님, 분리 트리거).
4. **의존 방향 단방향.** 안쪽(도메인/DB)이 바깥쪽(UI/HTTP)을 몰라야 한다. 화살표를 거스르는 import 금지.
5. **경계 = 계약.** 레이어 간에는 정해진 입출력(모델/DTO)으로만 대화한다.

## 1. 프론트엔드 (Flutter + Provider)

### 1-1. 폴더 구조
```
lib/
  main.dart
  app.dart                      # 앱 루트, Provider 등록, 라우팅 연결
  core/
    config/
      env.dart                  # API base URL, 스토리지 URL 등
      constants.dart
    network/
      api_client.dart           # HTTP 클라이언트 1개 (인터셉터·토큰 부착)
      api_exception.dart
    error/
      failure.dart              # UI가 다루는 실패 타입
    memory_date/                # 기억 날짜(YYYY.MM.DD + X) 규칙 — 백엔드 common/memory-date 와 같은 규칙
    utils/                      # 순수 헬퍼 (1파일 1기능)
  data/
    models/                     # 1파일 1모델 (DTO/데이터 클래스)
      place_pin_model.dart
      place_detail_model.dart
      event_pin_model.dart
      story_model.dart
      memory_date_model.dart
      ...
    datasources/                # 리소스별 원격 호출만 (HTTP + 파싱)
      place_remote_datasource.dart
      event_remote_datasource.dart
      story_remote_datasource.dart
      auth_remote_datasource.dart
      ...
    repositories/               # datasource → provider용 데이터 변환/조합
      place_repository.dart
      story_repository.dart
      ...
  providers/                    # 기능별 ChangeNotifier (상태만)
    map_provider.dart           # 장소·축제 핀 상태
    place_detail_provider.dart  # 장소 정보 + 타임라인
    event_detail_provider.dart  # 축제 정보 + 타임라인
    story_write_provider.dart   # 기록 작성(숫자판 날짜 포함)
    auth_provider.dart
    ...
  ui/
    screens/                    # 화면 1개 = 1파일
      map/
        map_screen.dart
        widgets/                # 그 화면 전용 위젯
          yeongcheon_map_view.dart
          place_marker_builder.dart
      place_detail/
        place_detail_screen.dart
      story_write/
        story_write_screen.dart
    widgets/                    # 여러 화면 공용 위젯 (1위젯 1파일)
      split_flap/               # 숫자판(공항 플랩) 위젯 — 날짜 입력·연도 머리글에 공용
      timeline/                 # 연도별 기록 타임라인(장소·축제 공용)
    theme/                      # 레트로 아카이브 테마(색·글꼴·ThemeData) — Sys_06
  routing/
    app_router.dart
```

### 1-2. 각 레이어의 책임
- **models**: 서버 JSON ↔ 객체. `fromJson`/`toJson`만. 로직 없음. 불변(immutable) 권장.
- **datasources**: HTTP 호출 + 응답 파싱. 한 파일 = 한 리소스. 비즈니스 판단 없음.
- **repositories**: 여러 datasource 조합, 에러를 `Failure`로 변환, provider가 쓰기 쉬운 형태로 반환.
- **providers**: 화면 상태 보관(ChangeNotifier). repository를 호출해 상태 갱신. **위젯을 모름**(UI 코드 없음).
- **ui/screens·widgets**: 표시와 사용자 입력만. provider를 `watch/select`로 구독. **HTTP·비즈니스 로직 금지**.

### 1-3. 의존 방향 (거스르면 안 됨)
```
ui  →  providers  →  repositories  →  datasources  →  (core/network)
                         └→ models (양쪽에서 참조 가능)
```

### 1-4. 분리 규칙 (Flutter)
- 위젯이 커지면 하위 위젯으로 추출해 `widgets/`에 뺀다(빌드 메서드가 화면을 꽉 채우면 신호).
- provider가 여러 화면 관심사를 담으면 기능별로 쪼갠다(map / place_detail / story 분리).
- 모델은 반드시 파일 1개당 1클래스.

## 2. 백엔드 (NestJS)

### 2-1. 폴더 구조 (리소스별 모듈)
```
src/
  main.ts
  app.module.ts
  common/
    filters/
      http-exception.filter.ts   # 전역 에러 → 공통 실패 envelope
    interceptors/
      response.interceptor.ts    # 성공 응답 → { success, data } 래핑
    guards/
      jwt-auth.guard.ts
    decorators/
      current-user.decorator.ts
    dto/
      pagination.dto.ts
  config/
    config.module.ts             # 환경변수 로드·검증
  database/
    data-source.ts               # DB 연결
    migrations/                  # 스키마 마이그레이션 (ERD v5 기준)
  modules/
    auth/
      auth.module.ts
      auth.controller.ts         # HTTP 입출력만
      auth.service.ts            # 인증 로직
      dto/
        signup.dto.ts
        login.dto.ts
    user/
      user.module.ts user.controller.ts user.service.ts user.repository.ts
      entities/user.entity.ts
      dto/
    place/
      place.module.ts place.controller.ts place.service.ts place.repository.ts
      entities/place.entity.ts
      dto/
    story/
      story.module.ts story.controller.ts story.service.ts story.repository.ts
      entities/story.entity.ts story-photo.entity.ts
      dto/ create-story.dto.ts query-story.dto.ts
    event/
    upload/                      # 프리사인 URL 발급
    achievement/
```

### 2-2. 각 레이어의 책임
- **controller**: 라우팅·요청 검증(DTO)·응답 반환만. **비즈니스 로직·DB 접근 금지.** service만 호출.
- **service**: 비즈니스 로직. 여러 repository 조합, 규칙 검증(예: 스토리 앵커 규칙). **HTTP 개념 없음**(응답 envelope을 직접 만들지 않음).
- **repository**: DB 접근(쿼리)만. service에만 노출.
- **DB 모델**: ORM은 **Prisma**. 모든 모델을 `prisma/schema.prisma` 한 곳에 정의(별도 entity 파일 없음). repository는 `PrismaService`로 접근.
- **dto**: 요청/응답 형태 + 검증 규칙. 엔드포인트 입력 경계에서만 사용.
- **common/filters·interceptors**: 응답 `{ success, data }` / 에러 `{ success, error }` 표준화를 **한 곳에서** 처리(각 컨트롤러가 반복하지 않음).

### 2-3. 의존 방향
```
controller  →  service  →  repository  →  (database)
      └→ dto            └→ entities
```

### 2-4. 분리 규칙 (NestJS)
- **리소스 1개 = 모듈 1개** = controller/service/repository/entity/dto 세트.
- service가 커지면 **유스케이스별로 분리**한다(예: `story.service` → `story-create.service`, `story-query.service`)까지 쪼갠다.
- DTO는 목적별 1파일(`create-story.dto.ts`, `query-story.dto.ts`).
- 공통 로직(응답 래핑·에러·인증)은 `common/`에 두고 재사용. 컨트롤러에서 중복 금지.

## 3. 공통 규약 (양쪽 레포)

### 3-1. 네이밍
- 백엔드(Nest) 파일: kebab-case (`story-query.service.ts`), 클래스: PascalCase.
- 프론트(Flutter) 파일: snake_case (`place_pin_model.dart`), 클래스: PascalCase.
- API JSON: camelCase / DB: snake_case (서버에서 매핑).

### 3-2. 에러·응답 표준
- API 명세서 v4의 envelope과 에러 코드 표를 **단일 출처**로 삼는다.
- 백엔드: 전역 필터/인터셉터로 강제. 프론트: `api_client`에서 envelope 해석 후 `Failure`로 변환.

### 3-3. 환경변수 (`.env`, 커밋 금지)
백엔드: `DATABASE_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `STORAGE_*`(외부 스토리지 키/버킷), `PORT`.
프론트: `API_BASE_URL`(dev/prod). `.env.example`만 커밋.

### 3-4. DB 마이그레이션
- ORM은 **Prisma**. 스키마 정본은 `prisma/schema.prisma`, 변경은 Prisma Migrate로만(수동 DB 편집 금지). ERD v5가 스키마 설명서.

### 3-5. 테스트 (검토 보조)
- 백엔드: service 단위 테스트로 핵심 규칙(예: 스토리 앵커 검증, 기억 날짜 범위 계산·정렬) 최소 커버.
- 사람이 전수 검토하는 대신, 규칙이 깨지면 테스트가 잡도록.

## 4. 아직 정할 것 (구현 착수 전)
1. (확정) ORM = Prisma **7**. `prisma/schema.prisma` 정본 + `prisma.config.ts`(CLI 설정) + `PrismaService`(pg 드라이버 어댑터)로 repository 구현. 생성 클라이언트는 `src/generated/prisma`(커밋 제외).
2. 외부 스토리지 종류(S3 / R2 …)와 프리사인 방식.
3. (확정) 프론트 라우팅 = **기본 Navigator + named route** (`routing/app_routes.dart` 이름·인자, `routing/app_router.dart` 생성). 화면이 많아지면 그때 패키지 검토.
4. Git 브랜치 전략·PR 규칙(레포별 README).
5. (확정) 지도 SDK = **네이버 지도(flutter_naver_map)**. 과거 배경 지도(era_map_layer)는 2026-10-10 시대 제거와 함께 **삭제**되어 타일 오버레이 문제는 해소됨.
7. (확정, 2026-10-10) **시대 제거.** 시간축 = 기록의 기억 날짜(`YYYY.MM.DD`, 모든 자리 X 허용). 범위·정렬 규칙은 ERD v5 §2–3. 같은 규칙을 백엔드 `src/common/memory-date/`, 프론트 `lib/core/memory_date/` 두 곳에 구현하고 같은 사례 표로 테스트한다(규칙 변경 시 두 곳 + 문서 동시 수정).
6. 프론트 환경값은 `.env` 파일 대신 `--dart-define`(`API_BASE_URL`, `NAVER_MAP_CLIENT_ID`) 으로 주입한다(`core/config/env.dart`).
